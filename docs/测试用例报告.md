# Position Engine 测试用例报告

## 一、项目概况

Position Engine 测试分为两层：

- **内部单元测试**（`#[cfg(test)] mod tests`）：嵌入在 `risk.rs` 和 `tracker.rs` 源码中
- **外部集成测试**（`src/position/test/`）：独立测试目录

## 四、遗漏场景分析

### 4.1 高优先级遗漏（影响核心逻辑）

#### 4.1.1 引擎命令处理（engine.rs）

以下场景**完全无测试**：

**handle_open_position：**
- 重复开仓拒绝
- 杠杆设置失败
- 风控拒绝后事件发出
- 下单成功后 Position/Order 状态

**handle_close_position：**
- 不存在的 `position_id`
- 零仓位平仓
- 平仓方向正确性（Long -> Sell, Short -> Buy）

**handle_cancel_order：**
- 不存在的 `order_id`
- 无 `exchange_order_id` 的订单

**handle_cancel_all_orders：**
- 通过 `position_id` 查找 symbol
- 无参数取消全部

**handle_modify_position：**
- 更新 `stop_loss` / `take_profit`

**ws_feed_loop OrderUpdate：**
- 未知 order 忽略
- 部分成交 Trade 创建
- 开仓加权平均 `entry_price`
- 平仓 size 归零后 Closed
- Position 从 DashMap 移除

**sync_loop 差异检测：**
- 外部开仓检测
- size 不一致 warn
- 资金费率检查触发 `RiskAlert`
- 强平预警触发 `LiquidationWarning`

**recover_state：**
- 从 DB 加载未关闭 Position
- 恢复 PnlTracker

#### 4.1.2 持久化层（persistence.rs）

**完全无测试：**
- `init_tables` SQL 正确性
- `upsert_position` ON CONFLICT 行为
- `update_order` 只更新指定字段
- `get_open_orders` 过滤条件
- `PnlSnapshot` 写入和读取

#### 4.1.3 适配器（binance_position_adapter.rs）

**完全无测试：**
- 类型转换正确性（`Order.id` String -> Uuid、Ticker 字段映射、`FundingRate.next_funding_time`）
- `place_order_with_options` 参数传递
- `cancel_all_orders` 遍历逻辑
- `get_balance` USDT 过滤
- `subscribe_order_updates` 返回空 channel

## 五、错误分析

当前 78 个外部测试全部通过，无逻辑错误。但存在以下潜在问题：

### 5.1 risk_tests.rs 边界歧义

**测试：** `test_funding_rate_exceeds_threshold`

**问题描述：** 注释说"0.002 < 2\*0.001=0.002，刚好不超过 2 倍"，但 `0.002 == 2*0.001`，是否应为 warning 还是 critical 取决于实现中用 `>` 还是 `>=`。当前测试断言 `severity="warning"`，如果实现用 `>=` 则应为 critical。

**建议：** 确认实现中的比较运算符，并据此调整测试断言或实现逻辑。

### 5.2 engine.rs total_equity 硬编码

**位置：** `handle_open_position`

**问题描述：** `total_equity` 硬编码为 `0.0`，导致单品种/总仓位上限检查中 `limit=0`，任何有 margin 的开仓都会被拒绝。这是一个已知 bug，但当前没有测试覆盖这个场景。

**建议：** 修复硬编码问题，并添加测试验证 `total_equity` 正确传入风控检查。

### 5.3 tracker.rs 内部测试与实际行为不一致

**测试：** `test_drawdown`（内部单元测试）

**问题描述：** 内部测试使用 `record_trade` 更新 peak，但实际代码中 `record_trade` 不更新 peak，只有 `update_unrealized` 才更新。内部测试的断言 `assert_eq!(tracker.peak_equity(), 15000.0)` 能通过是因为 `snapshot()` 内部计算了 equity 并隐式更新了 peak。

**影响：** 外部测试 `test_max_drawdown_calculation` 正确地指出了这个行为差异。内部测试虽然通过，但测试路径与实际使用路径不一致，降低了测试的有效性。

**建议：** 修改内部测试使用 `update_unrealized` 来更新 peak，使其与实际代码路径一致。
