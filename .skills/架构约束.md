# virs 架构约束

开发时必须严格遵守以下架构与风格约束。每条约束均来自现有代码的实际模式，新增代码必须与现有风格一致。

---

## 1. 六层分层拓扑

工作区采用严格的 6 层分层架构，依赖只能向下流动，禁止同层互相依赖、禁止反向依赖。

| 层级 | 目录 | Crate | 职责 |
|------|------|-------|------|
| L0 foundation | `crates/foundation/` | `virs-error`, `virs-task` | 零 VIRS 依赖的基础设施 |
| L1 infra | `crates/infra/` | `virs-type`, `virs-utils`, `virs-config`, `virs-ws`, `virs-llm` | 基础类型、工具、配置、WS、LLM 客户端 |
| L2 core | `crates/core/` | `virs-indicator`, `virs-ccxt`, `virs-exchange`, `virs-prompt` | 技术指标、交易所对接、交易所抽象、策略提示词 |
| L3 services | `crates/services/` | `virs-market`, `virs-position`, `virs-trading-bot`, `virs-tactical-bot` | 行情引擎、持仓引擎、交易机器人、战术机器人 |
| L4 api | `crates/api/` | `virs-api` | HTTP API 层 |
| L5 app | `apps/server/` | `virs-app` | 应用组装层，唯一二进制 |

### 依赖方向铁律

- 每层只能依赖比自己层级更低的 crate
- 同层 crate 之间禁止互相依赖（如 `virs-prompt` 不能依赖 `virs-indicator`）
- 如果两个同层 crate 需要共享类型，类型必须下沉到更底层（如 `virs-type`）
- `virs-error` 和 `virs-task` 是 L0，不依赖任何 VIRS crate

## 2. virs-type 类型层约束

`virs-type` 是工作区的类型契约层，只包含基础数据类型和接口 trait 定义，不包含任何业务逻辑实现。

### 模块组织

每个领域子模块遵循 `mod.rs` + `enums.rs` + `structs.rs`（+ 可选 `traits.rs`）三件套：

```
virs-type/src/
├── lib.rs              ← 声明所有子模块，pub use 扁平导出
├── bot/
│   ├── mod.rs          ← mod enums; mod structs; mod traits; pub use *::*;
│   ├── enums.rs
│   ├── structs.rs
│   └── traits.rs       ← OrderExecutor, CredentialStore, MarketDataProvider, LlmProviderResolver, KlineEventSource, KlineEngineHandle, OrderBookEngineHandle, PositionEngineHandle, BotStore, TradeHistoryProvider
├── exchange/
│   ├── mod.rs
│   ├── enums.rs
│   ├── structs.rs
│   └── traits.rs       ← ExchangePe
├── indicator/
│   ├── mod.rs
│   ├── enums.rs        ← IndicatorSpec, IndicatorValue
│   └── structs.rs      ← IndicatorSet（数据容器，计算逻辑在 virs-indicator）
├── market/
│   ├── mod.rs
│   ├── enums.rs        ← Timeframe 等
│   └── structs.rs      ← Kline, MarketSnapshot, MarketInfo 等
├── order/
│   ├── mod.rs
│   ├── enums.rs
│   └── structs.rs
├── position/
│   ├── mod.rs
│   ├── enums.rs
│   └── structs.rs
├── llm/
│   ├── mod.rs
│   └── structs.rs
└── ws_types.rs         ← 顶层单文件
```

### 类型层铁律

- `virs-type` 只定义 `enum`、`struct`（纯数据）和 `trait`（接口签名）
- struct 只有字段和 derive 宏，不写业务方法（数据访问方法如 `get_num()` 除外）
- trait 只有方法签名，不写业务实现（少量默认实现如复用查询可以接受）
- 所有类型通过 `lib.rs` 的 `pub use *::*` 扁平导出，下游直接 `use virs_type::TypeName`
- 纯数据类型（如 `IndicatorSpec`、`IndicatorValue`、`IndicatorSet` 数据容器）放在此层，计算逻辑放在上层 crate
- `virs-type` 的依赖仅限 `serde`、`chrono`、`uuid`、`sqlx`、`virs-error`，不引入任何业务 crate

### 类型下沉原则

当两个同层 crate 需要共享类型时，必须将类型下沉到 `virs-type`：

- 示例：`virs-prompt` 和 `virs-indicator` 同属 L2，都需要 `IndicatorSpec` → 类型定义在 `virs-type` (L1)，两个 crate 各自从 `virs_type` 导入
- `virs-indicator` 保留计算逻辑（`compute_indicators` 函数），不 re-export 类型，下游直接从 `virs_type` 引入

## 3. virs-error 错误处理约束

`virs-error` (L0) 是工作区唯一的错误定义 crate。

### 错误收敛机制

```
BotError (virs-error/bot.rs)      ──┐
ExchangeError (virs-error/exchange.rs) ──┤
sqlx::Error                        ──┼──→  VirsError (virs-error/lib.rs)
                                   │     (顶层收敛枚举, #[from] 自动转换)
anyhow::Error                      ──┘
```

### 错误处理铁律

- 其他 crate 禁止定义自定义错误类型，禁止 `Result<_, String>`，禁止直接调用 `anyhow`
- 子错误用 `thiserror` 派生，通过 `#[from]` 自动提升为 `VirsError`
- `virs-error` 是唯一声明 `anyhow` 依赖的 crate；其他 crate 用 `use virs_error::Context` 获取 `.context()`
- `?` + `.context()` 将错误收敛为 `VirsError`
- 错误分类通过 4 个 trait 实现：`Retryable`、`Categorized`（ErrorCategory 枚举）、`HttpStatus`、`ErrorCode`
- 重型依赖（axum、sqlx、reqwest）通过 feature gate 按需引入，保持 L0 轻量

## 4. virs-task 任务管理约束

`virs-task` (L0) 是工作区唯一的异步任务管理 crate。

### 任务管理铁律

- 所有异步任务（周期任务、延迟任务、一次性任务）必须通过 `virs_task::spawn` 或 `virs_task::spawn_periodic` 创建
- 禁止直接使用 `tokio::spawn` 或 `tokio_util::sync::CancellationToken`
- `spawn(name, f)` 闭包签名 `FnOnce(Stop) -> Fut`，强制接收 `Stop` 取消令牌
- `spawn_periodic` 内置 panic 隔离：单次执行 panic 不影响后续周期循环
- `TaskHandle` 通过 RAII（Drop 自动 cancel）+ 超时 abort 保证资源不泄漏
- 每个任务实例必须完全独立：独立创建、独立销毁/取消、无共享状态

## 5. 可见性与工厂函数模式

具体实现类型用 `pub(crate)` 隐藏，通过 `pub fn create_*` 工厂函数暴露 trait object 或 Handle。

### 模式规范

```rust
/* 实现类型对 crate 外不可见 */
pub(crate) struct KlineEngine { ... }

impl KlineEngine {
    pub(crate) fn new(...) -> Self { ... }
    pub(crate) async fn run(&self, stop: Stop) { ... }
}

/* 工厂函数是唯一的外部创建入口，返回 trait object */
pub fn create_kline_engine(
    config: KlineEngineConfig,
    source: Arc<dyn KlineSource>,
    perpetual_ws: Arc<Mutex<dyn KlineWsClient>>,
) -> Arc<dyn KlineEngineHandle> {
    Arc::new(KlineEngine::new(config, source, perpetual_ws))
}
```

### 工厂函数返回类型约定

| 场景 | 返回类型 | 示例 |
|------|---------|------|
| 引擎/服务组件 | `Arc<dyn TraitHandle>` | `create_kline_engine → Arc<dyn KlineEngineHandle>` |
| 需要运行循环的引擎 | `(Sender, TaskHandle)` | `create_bot_engine → (mpsc::Sender<BotCommand>, TaskHandle)` |
| 交易所适配器 | `Box<dyn Trait>` | `create_exchange → Box<dyn ExchangePe>` |
| 策略热替换 | `(Arc<dyn Trait>, TaskHandle)` | `create_strategy_engine → (Arc<dyn StrategyHotSwapSource>, TaskHandle)` |

### run() 方法处理

- 如果实现类型有 `async fn run(&self, stop: Stop)` 方法，工厂函数内部调用 `virs_task::spawn` 启动 run 循环，返回 Handle 而非暴露 run 方法
- 如果实现类型有 `fn start(self: Arc<Self>) -> TaskHandle` 方法，工厂函数内部克隆 Arc 并调用 start，返回 Handle

## 6. Trait 抽象约定

跨 crate 解耦通过 trait 实现，trait 定义集中在 `virs-type`，部分定义在领域 crate 中。

### Trait 定义位置

| 位置 | Trait | 说明 |
|------|-------|------|
| `virs-type/src/bot/traits.rs` | `OrderExecutor`, `CredentialStore`, `MarketDataProvider`, `LlmProviderResolver`, `KlineEventSource`, `KlineEngineHandle`, `OrderBookEngineHandle`, `PositionEngineHandle`, `BotStore`, `TradeHistoryProvider` | 交易核心接口与持久化 |
| `virs-type/src/exchange/traits.rs` | `ExchangePe` | 交易所接口 |
| `virs-type/src/ws_types.rs` | `KlineWsClient`, `OrderBookWsClient` | WS 客户端 |
| `virs-prompt/src/lib.rs` | `PromptProvider`, `StrategyHotSwapSource` | 策略提示词 |
| `virs-market/src/types.rs` | `KlineSource` | K 线数据源 |
| `virs-position/src/persistence.rs` | `PositionPersistence` | 持仓持久化 |

### Trait 约定

- 所有跨 crate trait 必须标注 `Send + Sync`
- 异步方法使用 `#[async_trait]` 宏
- App 层（`virs-app`）在组装时将具体实现强制转换为 `Arc<dyn Trait>` 或 `Box<dyn Trait>`
- trait object 协变：如果 `KlineEngineHandle: KlineEventSource`，则 `Arc<dyn KlineEngineHandle>` 可直接传给接收 `Arc<dyn KlineEventSource>` 的函数

## 7. 注释规范

### 铁律

- 仅使用 `/* */` 格式注释，禁止 `//`、`///`、`//!`
- 所有注释使用中文
- 注释必须与代码逻辑一致，描述为什么而非是什么

### 注释场景

```rust
/* 类型/结构体文档：说明职责和用途 */
pub struct PromptTemplate { ... }

/* 函数文档：说明功能、参数含义、关键约束 */
pub fn create_strategy(template: &PromptTemplate) -> BotResult<PathBuf> { ... }

/* 行内逻辑说明：解释非显而易见的业务逻辑 */
let unique: HashSet<&IndicatorSpec> = specs.iter().collect();

/* 多行文档：用于复杂函数的详细说明 */
/* 创建新策略：在 STRATEGIES_DIR 下创建策略文件夹和 v{version}/ 版本文件夹，写入提示词文件和 meta.json。
   策略文件夹不能已存在。meta.json 最后写入以确保原子性——崩溃时不会留下不完整的策略。 */
```

## 8. 测试规范

### 文件命名

- 单元测试文件命名：`{tested_file_name}_tests.rs`，与被测文件同目录
- 在 `mod.rs` 中声明：`#[cfg(test)] mod {tested_file_name}_tests;`
- 集成测试放在 `tests/` 目录下，命名 `integration_tests.rs`

### 测试文档

- 每个 crate 根目录必须有 `test_plan.md`，使用中文编写
- 内容包含：编号、测试函数名、测试场景、输入数据、预期结果
- 文档中的测试总数必须与实际测试数量一致

### 示例

```
| 编号 | 测试函数名 | 场景 | 输入数据 | 预期结果 |
|------|-----------|------|---------|---------|
| 1 | test_create_strategy_success | 创建新策略 | 合法 PromptTemplate | 返回策略路径，文件存在 |
```

## 9. 日志规范

### 铁律

- 使用 `tracing` 宏（`info!`、`warn!`、`error!`、`debug!`），禁止 `println!`/`print!`/`dbg!`（workspace lint deny）
- 结构化字段：`key = %value`（Display）或 `key = ?value`（Debug），消息字符串放最后
- 消息使用中文
- 日志必须包含完整上下文：`bot_id`、`symbol`、`client_order_id` 等关键标识
- 相同操作语义的日志级别必须跨模块一致（如交易持久化失败在 bot worker 中使用相同级别）

### 日志级别约定

| 级别 | 使用场景 |
|------|---------|
| `info!` | 引擎启动/停止、策略创建/删除、连接建立 |
| `warn!` | 字段缺失降级处理、非致命错误、重试、配置缺失 |
| `error!` | 数据库操作失败、连接失败、严重解析错误 |
| `debug!` | 详细调试信息 |

### 示例

```rust
tracing::info!(
    path = %strategy_dir.display(),
    name = %template.name,
    version = template.version,
    "策略已创建"
);

tracing::warn!(
    symbol = %symbol,
    "Ticker closeTime 缺失 — 回退使用 Utc::now()"
);
```

## 10. 策略文件系统结构

### 目录结构

```
strategies/                          ← 环境变量 STRATEGIES_DIR 指向
├── meta.json                        ← 根级元数据（共享 output 格式路径）
├── output.md                        ← LLM 输出格式模板
├── {strategy_name}/
│   ├── meta.json                    ← 策略元数据（路径索引 + version 字段）
│   └── v{version}/
│       ├── system_prompt.md
│       ├── user_prompt_template.md
│       ├── required_placeholders.json
│       └── description.md
```

### 路径解析规则

- `meta.json` 中的路径字段使用 `./` 前缀（如 `"./system_prompt.md"`），表示相对于版本文件夹
- `MetaFile::filename(path)` 去掉 `./` 前缀，拼接 `v{version}/` 定位实际文件
- `MetaFile::from_template()` 是路径字符串的唯一 source of truth
- writer 和 loader 统一通过 `MetaFile::filename()` 解析路径

### 写入原子性

- `meta.json` 最后写入，确保崩溃时不留下不完整的策略
- 创建新版本时（`v{N+1}/`），不修改旧版本文件，仅更新 `meta.json` 的 `version` 字段

### LLM 生成约束

- LLM 示例中的占位符名称必须与 `placeholder::all()` 白名单完全一致
- 占位符双向校验：模板中使用的必须在 `required_placeholders` 中声明，声明的必须在模板中使用

### 强制 deny（编译失败）

| Lint | 说明 |
|------|------|
| `dbg_macro` | 禁止 `dbg!()` |
| `todo` | 禁止 `todo!()` |
| `unimplemented` | 禁止 `unimplemented!()` |
| `print_stdout` | 禁止 `println!()`/`print!()` |

### warn 级别（需修复）

`clone_on_copy`、`needless_return`、`needless_borrow`、`manual_strip`、`manual_unwrap_or`、`question_mark`、`new_without_default`、`should_implement_trait` 等。

## 12. 关键业务约束

### 交易参数

- 关键交易参数（fill_price、liquidation_price、leverage、order direction、fee、filled quantity、original_price、upper_price、lower_price、grid_profit_pct、quantity_per_grid、market_regime、marginType）禁止设置默认值，缺失时必须通过 `virs-error` 抛出错误

### CcxtOrder

- `CcxtOrder` 只包含交易所原生响应字段，禁止添加 `created_at`、`updated_at` 等业务字段

### 持仓管理

- 持仓状态在重启时通过聚合 `pe_orders` 表恢复，不使用 `pe_positions` 表
- Position ID 使用确定性 UUID v5（基于 exchange + symbol + position_side 生成），确保跨重启稳定
- 仅支持 Hedge（双向持仓）模式，OneWay 模式必须拒绝
- `Position.quantity` 在部分成交时更新，确保数据一致性
- `Position.entry_price` 必须使用 `last_fill_price`（边际价格）而非 `avg_fill_price`（累计均价），避免双重计算

### 交易所数据

- Binance WS `S` (side) 字段只能为 `BUY` 或 `SELL`（大写），未知值通过 `virs-error` 抛出错误并跳过该订单
- `OrderBook` 必须包含 `last_update_id` 字段以支持 WS 增量深度同步
- `OrderBook.timestamp` 使用交易所原生 `T`（交易时间）字段，回退到 `E`（事件时间）再回退到 `Utc::now()`
- `Ticker.timestamp` 使用交易所原生 `closeTime` 字段，回退到 `Utc::now()`

### Bot 类型

- Bot 类型必须为 `chat` 或 `agent`，数据库 CHECK 约束保证
- `agent` 类型仅存储，尚未实现运行逻辑
- 运行中的 Bot 不能更改 `bot_type`，必须先停止再修改再重启

### 策略绑定

- Bot 的 `strategy_file` 在创建时绑定，不能为 NULL
- 运行中的 Bot 不能更新 `strategy_file`，必须先停止再更新再重启

### LLM 客户端

- LLM 客户端必须设置应用层超时，防止无限挂起
